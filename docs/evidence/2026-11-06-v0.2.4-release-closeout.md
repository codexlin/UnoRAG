# UnoRAG v0.2.4 发布收口验收

> 日期：2026-11-06，Asia/Shanghai。机器与流水线原始记录使用 UTC。
> 候选提交：`339307e689bd4e484b6d5891c3aa9a86fce17b34`。
> 当前结论：**隔离候选 GO；最终稳定镜像及香港正式实例复验 GO**。

## 验收范围

本轮先修正真实观察，再验证交付与恢复，最后构建稳定版。PR #195/#196 的增量不新增业务功能、服务、
必需配置或数据库迁移；公开 Knowledge API 字段兼容。v0.2.4 仍包含此前主干的迁移，升级必须运行
随版本发布的 migrator，不能只替换 Web 镜像。测试语料、黄金答案和 15 秒 P95 门槛均未修改。

- 参考环境：香港原生 Linux/amd64，2 vCPU、约 4 GiB 内存；不是 ARM 模拟运行。
- 隔离项目：`unorag-rc-closeout`，独立 PostgreSQL、Qdrant、Redis、文件卷与管理员凭据。
- 隔离边缘仅绑定 `127.0.0.1:8096`，浏览器经 SSH tunnel 访问，不对公网暴露验收入口。
- 隔离恢复使用 local 存储；正式实例使用 COS。正式数据未用于破坏性删卷恢复。
- 模型与解析使用真实 Provider，入库写入真实 Qdrant。故障代理只在明确的故障步骤中启用。
- 不启动完整 Ops Stack 或自托管 Langfuse，不扩大为公网多租户或无限容量认证。

## 问题与修复

### 新建库被后台轮询打断

旧版本的写后刷新与后台轮询共用会取消在途请求的刷新函数。轮询可取消新建库后的权威刷新，导致
后续选中操作没有执行，列表稍后出现新库但仍选中旧库。对实际香港旧版本 `b0222ea` 的受控响应
重现了该问题，没有写入正式测试库。

[PR #195](https://github.com/codexlin/UnoRAG/pull/195) 将后台刷新改为加入/去重已有请求，保留变更后
主动取消旧快照的语义。真实 QueryClient 回归、桌面/移动受控竞态，以及不拦截网络的实际创建均通过。
实际创建验证保留一个真实排队上传任务，暂时暂停隔离 Worker，选中新库后跨过多次轮询；之后恢复
Worker，确认上传完成并清理测试资料。该控制条件不等同于上游解析正在计算。

### PDF 分阶段耗时不可区分

新增 `parser_report.metrics.parser_timing` 与文档详情展示，将本地分析、提交、观察到完成前的任务等待、
结果获取/转换分开，记录应用层轮询和重试次数。详细日志按 Job ID 关联，Provider task ID 仅保留摘要。
旧报告或失败任务缺失汇总时不补零。计时不进入索引记录或重放清单，已有测试验证不改变检索载荷。

本轮新鲜入库的实际观测，单位为秒：

| PDF | 本地分析 | 提交 | 任务等待 | 结果获取/转换 | 轮询 |
|---|---:|---:|---:|---:|---:|
| crosstable-large | 0.140 | 1.668 | 17.593 | 0.545 | 24 |
| mixed-charts | 0.015 | 1.654 | 9.815 | 0.571 | 14 |
| scan-lowcontrast | 0.004 | 1.749 | 9.508 | 0.323 | 14 |
| twocolumn | 0.020 | 1.551 | 9.884 | 0.497 | 13 |

四份均实际走 MinerU、完成入库，应用层重试为零。任务等待包含轮询、网络和间隔，不能据此推断上游
排队时间或模型纯计算时间；本地 Job 排队也与这些阶段分开。

### 在途请求越过解析预算

真实本地 HTTP 探针延迟响应 500ms，旧代码只在操作之间检查预算，且预算从提交后才开始：

| 操作 | 配置预算 | 修复前 | 修复后 |
|---|---:|---|---|
| 提交 | 50ms | 554ms，错误地成功 | 54ms，provider_timeout |
| 轮询 | 50ms | 530ms，迟到的超时 | 52ms，provider_timeout |
| 结果获取 | 50ms | 542ms，错误地成功 | 53ms，provider_timeout |

[PR #196](https://github.com/codexlin/UnoRAG/pull/196) 从提交开始共享预算，贯穿源读取、上传、创建任务、
轮询、下载、响应体与转换；将中断信号传递到 self-hosted MinerU 和 302.AI 请求。迟到结果不继续
激活，取消中的 HTTP 操作会被中断，上游取消通知最多等待一秒。十个新增真实 HTTP 回归覆盖四个阶段
的响应头/体、302 ZIP 与取消端点卡住；原有解析测试合计 32/32 通过。

边界：这是一次 ParserProvider 执行的预算，不是包含所有 DBOS 重试/退避的整个 Job 总时限。
本地预分析另有 LiteParse 执行预算；不能强制终止同进程原生 CPU 计算。可重试失败保持幂等键，
不保证上游任务已停止，302.AI 也没有远程取消端点。

## 失败记录与复验边界

- 早期开发服务器的完整浏览器结果为 29/32：两项生产响应头断言不适用于 dev，另有同时运行的
  Playwright 输出目录冲突。改为独立生产构建、独立输出目录后完整 32/32；没有放宽响应头断言。
- 辅助下载脚本最初误用复用轮次报告中为空的 documentId；该轮没有新入库 Job，不能据此断言原文丢失。
  后续通过产品文档列表解析 ID，并对七份实际原文进行恢复前后摘要校验。
- 七文件扩展恢复中，官方异步恢复自身通过，但外层辅助脚本在 `spawnSync` 后首次登录出现 EPIPE。
  保留失败快照，用异步子进程重放同一备份并完成原文、版本和问答核对；没有给产品盲加网络重试。
- 香港宿主机没有 pnpm，未把宿主机 offline preflight 写成 PASS。代码门禁由精确提交的 Node 22 CI
  与本地真实依赖测试证明；宿主机额外 Node 只作为隔离验收工具，不新增产品服务。
- 历史 b0222ea/d9b1377/c066377 的报告和失败结果仍保留。本次 PASS 不改写历史结论。
