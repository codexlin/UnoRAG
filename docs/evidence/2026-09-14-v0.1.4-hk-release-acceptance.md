## 发布门禁与修复

`v0.1.3` 候选在镜像签名前被 Trivy 正确阻断：Node/Debian 基础镜像包含
`libpcre2-8-0 10.42-1`，命中 CVE-2026-86145 与 CVE-2026-89161。该 tag 未创建 GitHub Release，
也未用于部署。`v0.1.4` 在 Web、Migrator、Ops 和 DBOS Worker 四条最终镜像路径中显式安装 Debian
安全修订，并增加发布安全回归测试。

本次还修复 DBOS Control 最小权限角色缺少 `app.ask_run_stages` 与 `app.job_stage_runs` 读取权限的
问题。部署角色验证与真实 PostgreSQL 集成测试同时覆盖这两个权限，避免运行中心阶段指标静默停止刷新。

## 香港环境原位升级

升级从 `v0.1.2` 的 digest-pinned 运行时执行。`v0.1.4` 没有新增 schema migration；服务器保留了此前
通过校验的升级前备份，本次参考环境热修复未额外生成重复备份。升级脚本完成以下步骤：

1. 校验 Release asset 的 SHA-256 与四个 GHCR 镜像的 Cosign 身份；
2. 进入维护模式并确认旧 DBOS application 和系统队列全部 drained；
3. 幂等应用迁移，重新配置数据库登录角色，并通过运行时权限验证；
4. 启动新 DBOS Worker/Control、Web 和 Caddy，执行 ACL reconciliation 与生命周期巡检；
5. 运行内置产品 smoke，并保留上一版镜像 pin 供应用级回滚。

内置 smoke 完整通过：

`login -> library A/B -> upload -> Ask -> Public Retrieve/Ask -> service-key scope -> isolation -> replace -> delete`

公网 readiness 返回 `status=ok`、`version=0.1.4`、正确 revision 和 Web digest；PostgreSQL、Qdrant、
模型与解析 Provider 均 ready，`degraded=false`。升级后四个实际发布镜像再次读取到
`libpcre2-8-0=10.42-1+deb12u1`。

## 残余边界

- 本次是单客户独立实例参考环境验收，不是公网共享多租户或任意客户拓扑认证。
- 未执行破坏性原地 restore；恢复能力仍以既有备份验证和客户自己的 RPO/RTO 演练为准。
- Library 创建、更新和删除的 CRUD 审计覆盖仍需统一补齐；文档上传、激活和运行链路审计不受影响。
- `v0.1.3` 仅保留为被安全门禁阻断的历史 tag，不应安装或创建发布资产。
