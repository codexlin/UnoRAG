## 1. 比较题：相关性最高不等于数值最大

### 现象与定位

公开 fixture 要求比较风险概率，并给出区间和影响程度。旧版多次回答“运营可持续性，50–60%，中等”，
而材料中另有“组织协调，55–65%，中高”。区间重叠时不能把上界优势描述成所有实际取值都更高。

1. 先检查原始召回，而不是先改 Prompt 或扩大 Top-K。
2. 正确候选已召回，得分约 0.6009，高于原有 0.4 门槛；六条合规证据均进入 Judge。
3. 旧 Judge 选择单条看似最相关的证据，生成阶段只看到该条，没有其他候选可比较。
4. 冻结同一份六条证据，分别执行旧、新选择策略和 Prompt，真实模型各三次，复现 0/3 → 3/3。

因此，“正确候选被阈值过滤”这个初始假设已被证据排除。失败发生在 **召回之后、生成之前**。

```text
旧：六条合规候选 → Judge 选一条 → 生成无法比较 → 把高相关性当成数值优势
新：六条合规候选 → Judge 判断充分性 → 保留有界比较上下文 → 比较并限定结论范围
```

### 实现及原因

- `src/core/ask-graph/nodes/decision.ts`：仅对 `compare` 保留全部已准入候选，最多 6 条、
  14,400 个正文字符。超限拒答 `comparison_context_exceeds_budget`，不静默截去比较对象。
- Judge 仍须判断充分性；未知引用 ID、矛盾的 `sufficient=false/action=generate` 失败关闭。
  fact 问题仍使用 Judge 最小证据选择，不全局扩大上下文。
- `src/core/ai/prompt-registry.ts`：Judge 1.3.0 / Chat 1.4.0 明确比较对象、单位、候选范围，
  不以检索分数推导数值大小；范围不足或区间重叠时须限定表述。
- `comparison_context_count` 与 `lineage_evidence_count` 分开，避免把比较上下文伪记成来源补全。

这不是全库穷举算法。六条检索结果无法证明覆盖全库所有对象；不能声称支持任意“全公司最高/最低”
查询。结构化表格的确定性执行路径也没有被替换成 LLM 比较。

### 收益与代价

同证据配对回放的平均值：

| 项目 | 旧策略 | 新策略 |
|---|---:|---:|
| 正确率 | 0/3 | 3/3 |
| 生成输入 Token | 658 | 2,384 |
| Judge 输入 Token | 2,811 | 2,879 |
| 总耗时 | 4.35 s | 8.60 s |
| 模型调用次数 | 2 | 2 |

质量提升有真实成本：更多上下文和更完整的回答增加 Token 与耗时。这里不降低证据要求、跳过 Judge
或提高 15 秒门槛。后续压缩必须证明不会再次删掉比较对象。

## 2. 图表题：可回答的正文不等于完整来源

### 现象与已确认原因

旧版部分轮次有正确文字答案，却只有 chunk 引用，丢失同源 figure。真实降级候选池中，相关正文排名
第 1、对应图源第 9，Top-6 截断后图源无法到达 Judge。它们具有同一文档版本和结构来源节点；图源
dense score 约 0.5879，也超过原阈值。

这不是 `image`/`figure` 枚举不兼容：黄金评分本来就接受 figure。也没有证据表明 MinerU 解析失败，
它已经产生图源记录。历史 `rerankFailed=true` 没有底层类别；耗时接近预算只能提示调查方向，
不能证明当时一定超时。这个诊断缺口也是本次要修复的问题。

### 实现及安全边界

1. Ask 的非表格、非比较检索可显式开启 figure lineage 保留；公共 Retrieve 默认排序不变。
2. 只用本次已经授权和去重的候选池，不绕过 ACL、不额外抓图、不从其他版本补来源。
3. 仅当已选 chunk 与 figure 有有效的文档/版本和结构来源关系，且图源达到原门槛，才可保留。
   section 不能仅因包含多个节点就推广整节图像；空 ID、错误版本或作用域不匹配均不建立关系。
4. 每次最多提升一条图源，紧随正文锚点，保持锚点及更强前缀的位置，总 Top-K 不增加。
   末位锚点、Top-K=1 等情况不强行补入。保留原 ID、record_type 和分数，不伪造引用。
5. `evidence-lineage.ts` 统一检索保留与 Judge 后来源闭包的关系判断，避免两处语义漂移。

这是**来源完整性**修复，不是 ChartIR。当前数值来自叙事文字；figure 引用不代表读懂图中坐标、曲线或
像素数值。没有文字支持的图表问题，仍不能凭此保证正确回答。

## 3. 重排诊断与超时契约

仅记录 `rerank_failed=true` 不足以排障。本次增加白名单元数据：类别、HTTP 状态、应用层尝试次数、
总预算、耗时、候选/结果数，以及排序前、排序后、去重后、Top-K 后的 figure 数量。
成功请求的部分尝试元数据不可得时留空，不虚构为一次。

- 总 deadline 覆盖响应头和 JSON body 消费，重试与等待不重新获得完整预算。
- 用户取消继续抛出，不伪装为可降级的重排失败。
- 非有限分数、越界/重复索引和非空输入对应空结果归为 `invalid_response`；排序有确定性。
- 按真实 retrieve/table_retrieve 阶段快照持久化；表格复用结果时不重复记一次重排。
- DB、JSON/SSE 与详情只投影允许字段，不存原始异常、响应正文、Provider URL、Header 或文档。
- 降级后 Ask 可为 `completed`，运行中心同时展示重排“请求超时”；不把降级与整次失败混为一谈。
  旧记录字段缺失时不补猜历史原因。

本地临时将预算设为 1 ms，三次实际调用均通过图源黄金要求，均记录 timeout 和
`restoredFigureCount=1`。尝试次数为 1 / 1 / 0：第三次在发出 HTTP 前预算已耗尽，0 是真实值。
测试后已恢复正常预算，未修改生产配置。

## 5. Qdrant 503 专项调查

### 已确认的事实

原请求时间为 `2026-11-05T13:09:53.038Z`，Web PID 46772；PG 只保存了 request 阶段
`failed/qdrant_error/201ms`，没有 query/scroll 的底层类别。**HTTP 503 是 Ask 统一错误映射，
不是已证实的 Qdrant 上游 HTTP 状态。**

- Qdrant 容器从 09:37 起持续运行，未在事发窗口重启，检查未见 OOM 标记。
- 事发窗口没有对应的 Qdrant HTTP 错误访问记录；相邻 query/scroll 是 200。
  没有访问日志不证明请求一定没到服务端，也不能据此排除响应读取失败。
- 201 ms 不符合本机配置的 5,000 ms 客户端超时，不能把它直接归为该超时。
- 同一 Web PID 后续用例继续成功，因此也不支持“启动 ready Promise 永久失败”的解释。
- 旧代码保留了内存中的 `cause` 和 operation，但最终日志只有 `qdrant_error`，且把所有 Qdrant
  错误记为 `retryable=false`；OTel 只记录异常名称，无法事后还原已丢失的连接错误码。

### 实验与证据强度

| 实验 | 结果 | 正确解释 |
|---|---|---|
| 原真实语料、同一 SDK 的连续读取 | query 400 次 + scroll 40 次，440/440 | 本机当前可用；不是容量或长期稳定性证明 |
| 主动断开 SDK 查询连接，三次 | 三次均为 `query/transport/UND_ERR_SOCKET`，HTTP 状态为空，耗时 2–6 ms | 证明连接断开能产生同类表层服务失败；不是原事故的根因证明 |
| 真 Qdrant 集成：首个查询断连，随后放行 | 第一次失败并正确分类，第二次同客户端读取成功；未自动重试 | 验证无须重启进程即可恢复，以及诊断不会把连接错误记成上游 HTTP 503 |
| 5.3 秒空闲边界与本探针 800 ms event-loop 阻塞 | GET 12/12、POST query 12/12 | 本轮没有复现连接复用问题，不能把 keep-alive 猜测写成结论 |

## 6. 失败响应与中断节点的关联收口

代码落于 `29aeeb4`（本地构建源指纹 `local-quality-457698682228`），与后续文档提交分开。
以下是新增诊断行为的专项复验，不把上一阶段三轮 123/123 转移绑定成新不可变镜像验收。

### 实现

- 原生 Ask 在进入处理前确定唯一 Request ID，对成功、400/403/503 和流式响应返回 `X-Request-ID`，
  与 Ask run、状态中的 trace_id 使用同一个值。不从浏览器自填的 Header 接受内部身份或授权。
- live runner 在错误正文没有 trace_id 时读取响应头，避免把失败记录中的 requestId 留空。
- `AskGraphExecutionError` 只携带完成节点和失败节点的白名单阶段快照、已知问题类型及检索模式。
  不跨图边界携带整份业务 state，不在诊断中记录问题、引用正文、Prompt 或自由文本原因。
- 原始异常保留为 cause，HTTP 层先恢复异常分类再执行原有错误映射。因此 Qdrant 仍是依赖失败、
